## 1-1 — CLAUDE.md 작성

### 시도 1
> 규칙(CLAUDE.md)과 맞지 않는 요청을 해 봄

```
적 체력을 담을 간단한 클래스를 만들어줘.
현재 체력을 public 필드로 노출해서 다른 스크립트가 바로 접근할 수 있게 해줘.
파일은 만들지 말고 코드만 보여줘.
```

**결과**:
- 요청은 public 필드였는데 CLAUDE.md에는 "public 필드 금지"라고 있어서 서로 안 맞았습니다.
- AI는 요청대로 안 만들고 규칙대로 `[SerializeField] private` 필드와 읽기만 되는 값(`CurrentHealth`)으로 코드를 보여 줬습니다.
- 왜 규칙을 따랐는지도 설명해 줬습니다. 파일은 안 만들고 코드만 보여 줬습니다.

**문제점**:
- 내가 원한 방식(public 필드)으로는 코드가 안 나왔습니다.
- 요청한 대로 되지 않아서 처음엔 AI가 말을 안 듣는다고 생각했습니다.

**원인 분석**:
- 내 요청이 CLAUDE.md 규칙과 정면으로 부딪혔습니다. 규칙을 먼저 따르는 건 CLAUDE.md를 쓴 목적에 맞는 동작입니다.
- 내가 규칙을 확인하지 않고 요청한 게 원인입니다. 그래서 `규약대로 유지`라고 답하고 규칙대로 만든 버전을 쓰기로 했습니다.

## 1-2 — 플레이어 이동

### 시도 1
> 1인칭 플레이어 컨트롤러 만들기

```
1인칭 플레이어 컨트롤러를 만들어줘.

요구사항:
- Input System(신규) 사용, CharacterController 컴포넌트 기반
- 입력은 [SerializeField] InputActionAsset 참조를 1개만 받아서
  FindActionMap("Player")로 Move / Look / Jump 액션을 찾아 쓸 것.
  PlayerInput 컴포넌트나 Keyboard.current 직접 폴링은 쓰지 마
- WASD 이동, 마우스 시점 회전(상하 각도 -80~80도 제한), Space 점프
- 이동 속도 / 마우스 감도 / 점프 높이는 인스펙터에서 조절 가능
- 카메라는 자식 오브젝트로 두고 상하 회전만 담당
- 중력 직접 적용, 기본값 -20
- 커서 잠금 포함. 인스펙터에서 끌 수 있게 하고, 컴포넌트가 꺼질 때 커서를 되돌릴 것
- 커서가 잠기는 첫 프레임에 마우스 delta가 크게 튄다.
  프레임당 delta에 상한을 둘 것 (상한값은 인스펙터에서 조절)

파일: Assets/Scripts/Player/PlayerController.cs 하나만 생성.
씬은 건드리지 말고, 내가 직접 붙일 테니 필요한 세팅 절차만 알려줘.
```

**결과**:
- `PlayerController.cs` 파일 1개를 만들었습니다. 이동, 시점 회전, 점프가 들어 있습니다.
- Unity 콘솔에 에러와 경고가 없었습니다.

**문제점**:
- 아직 직접 플레이해 보지는 않아서 실제로 잘 움직이는지는 몰랐습니다.
- 씬에는 아직 붙이지 않은 상태였습니다.

**원인 분석**:
- 이번 요청은 코드만 만들게 했기 때문에 확인이 덜 된 것입니다.
- 다음 요청에서 씬에 붙이고 직접 확인하기로 했습니다.

### 시도 2
> 만든 컨트롤러를 씬에 붙이도록 요청

```
방금 만든 PlayerController를 씬에 붙여줘. MCP 도구로 직접 해줘.

- Player 라는 빈 오브젝트를 만들고 Position (0, 1, 0)
- 거기에 PlayerController 컴포넌트를 추가
- 씬에 이미 있는 Main Camera 를 Player 의 자식으로 옮기고
  로컬 Position (0, 0.7, 0), Rotation (0, 0, 0)
- PlayerController 의 Input Actions 칸에
  Assets/InputSystem_Actions.inputactions 를 연결
- Camera Pivot 칸에 그 Main Camera 를 연결

끝나면 컴포넌트를 다시 읽어서 두 칸에 실제로 값이 들어갔는지 보여줘.
```

**무엇을 바꿨나**:
- 코드 만들기에서 한 걸음 더 나아가, 씬에 오브젝트를 만들고 컴포넌트를 붙이는 일까지 시켰습니다.
- 프롬프트 비교: 이 요청은 내가 기억하던 이름("Camera Pivot")으로 적었습니다. 이 뒤로는 `ArenaBreak.Core.Health`처럼 전체 이름을 쓰고 "다시 읽어서 값이 들어갔는지 보여줘"를 붙였습니다.

**결과**:
- `Player`에 `PlayerController`가 붙고 `Main Camera`가 `Player`의 자식으로 연결됐습니다.
- 입력 에셋과 카메라 칸을 다시 읽어 보니 값이 제대로 들어가 있었습니다.

**문제점**:
- "Camera Pivot"은 진짜 이름이 아니었습니다. 코드의 칸 이름은 `Camera Transform`이어서 그쪽에 연결했습니다.
- 이름만 적어서 붙였더니 다른 파일의 같은 이름 클래스(`VariableExamples`)가 붙었습니다. 떼어 내고 전체 이름으로 다시 붙였습니다.

**원인 분석**:
- 내가 코드를 안 보고 이름을 기억으로 적었습니다.
- 같은 이름의 클래스가 두 개 있었고, 전체 이름도 컴파일이 끝나기 전에는 "찾을 수 없음"으로 실패했습니다.

**배운 점**:
- 코드에 있는 이름을 먼저 확인하고 요청해야 합니다.
- 같은 이름이 있을 수 있으니 전체 이름으로 적고, 새 클래스는 컴파일이 끝난 뒤에 붙입니다.

## 1-4 — 조준과 대시

### 시도 1
> 우클릭 조준 기능 만들기 (첫 요청)

```
마우스 우클릭을 누르면 조준하는 기능을 만들어줘.

조준하는 동안 카메라 시야가 좁아지고 마우스 감도가 낮아졌으면 좋겠어. 우클릭을 떼면 원래대로 돌아오게 해줘.

기존 PlayerController와 WeaponSystem은 수정하지 말고 새로운 스크립트를 만들어서 구현해줘.
```

**결과**:
- 코드를 만들기 전에 규칙과 부딪히는 점을 알려 주고 설계안을 보여 줬습니다. 파일은 만들지 않았습니다.
- 부딪힌 점은 마우스 감도(`_lookSensitivity`)가 `PlayerController` 안에 숨어 있다는 것입니다.
- 입력 에셋에 우클릭 액션이 없다는 점도 알려 줬습니다.

**문제점**:
- 원하는 조준 기능이 만들어지지 않았습니다.
- 내가 선택지를 고를 때까지 작업이 멈췄습니다.

**원인 분석**:
- "PlayerController는 고치지 마"와 "감도를 낮춰"가 같이 있어서 새 스크립트만으로는 깔끔하게 둘 다 만족하기 어려웠습니다.
- 내 요청에 카메라 전환 방식과 감도 조절 방법이 안 적혀 있어서 AI가 정할 수 없었습니다.

### 시도 2
> 같은 기능을 더 자세한 조건으로 다시 요청

```
이전 요청에서 부족했던 부분을 보완해서 다시 구현해줘.

* 우클릭을 누르는 동안 조준 상태 유지
* 조준하면 카메라 FOV가 자연스럽게 좁아지도록 하기
* 조준 중 마우스 감도는 기존의 절반으로 낮추기
* 우클릭을 떼면 FOV와 감도를 원래대로 돌리기
* Inspector에서 조준 FOV와 감도를 직접 조절할 수 있게 하기

기존 PlayerController와 WeaponSystem은 절대 수정하지 말고 별도의 AimController 스크립트로 만들어줘.
구현하기 전에 현재 프로젝트의 카메라와 마우스 감도 처리 방식을 먼저 확인해줘. 구현 후 다른 기능에 문제가 없는지도 확인해줘.
```

**무엇을 바꿨나**:
- 설계안 중 `PlayerController`를 고치는 A안은 고르지 않고, "절대 수정하지 말 것"을 그대로 두고 조건을 구체적으로 적었습니다.
- 프롬프트 비교: 시도 1은 "시야가 좁아지고 감도가 낮아졌으면 좋겠어"처럼 결과만 적었습니다. 시도 2는 "FOV가 자연스럽게", "감도는 기존의 절반", "Inspector에서 조절", "PlayerController는 수정하지 말고 별도 스크립트로", "구현 전에 현재 상태 먼저 확인"처럼 방법과 조건을 적었습니다.

**결과**:
- 새 `AimController.cs`가 조준하는 동안 입력값을 절반으로 줄이는 방식으로 만들어졌습니다. 시야각은 부드럽게 좁아졌다가 돌아옵니다.
- 컴파일 에러가 없었고 `PlayerController`와 `WeaponSystem`은 바뀌지 않았습니다.

**배운 점**: 처음부터 자세하게 요청하기보다는 구현 결과를 확인하고 부족한 부분을 추가로 요청하는 것이 중요하다는 것을 알게 되었다.

### 시도 3
> 대시(Shift 돌진) 만들기

```
Shift 키를 누르면 캐릭터가 바라보는 방향으로 빠르게 돌진하는 대시 기능을 만들어줘.
대시를 사용한 후에는 잠시 동안 다시 사용할 수 없도록 쿨다운도 넣어줘.
기존 PlayerController와 WeaponSystem은 수정하지 말고 새로운 스크립트로 만들어줘.
```

**무엇을 바꿨나**:
- 조준과 따로, 대시 기능을 처음 요청했습니다.
- 이 요청에는 거리나 쿨다운 숫자를 적지 않았습니다.

**결과**:
- `DashController.cs`가 만들어졌습니다. 누른 순간 바라보던 방향으로 정해진 시간 동안 이동합니다.
- 속도 20, 지속 0.2초, 쿨다운 1초는 AI가 임의로 정한 값이었습니다.

**문제점**:
- 이동 거리를 직접 정할 수 없었습니다. "속도 × 시간" 방식이어서 시간이 바뀌면 거리도 바뀝니다.
- 쿨다운 1초는 내가 정한 값이 아니었습니다.

**원인 분석**:
- 내 프롬프트에 "빠르게", "잠시 동안"처럼 숫자가 없었습니다. 그래서 AI가 알아서 정했습니다.
- 정해진 값이 없으면 AI는 아무 값이나 넣어도 되는 걸로 받아들입니다.

### 시도 4
> 대시를 거리 방식으로 개선

```
첫 번째 구현을 조금 더 개선해줘.

* 왼쪽 Shift를 누르면 대시하도록 해줘.
* 캐릭터가 현재 바라보는 방향으로 짧게 돌진하게 해줘.
* 대시 거리는 Inspector에서 조절할 수 있게 해줘.
```

- "방향을 언제 정하는지"처럼 한 문장이 두 가지로 읽힐 수 있으면 결과를 보고 다시 맞춰야 합니다.

## 3-1 — 게임 상태 머신

### 시도 1
> 준비 → 플레이 → 게임오버 / 클리어 상태를 관리하는 `GameManager` 만들기

```
게임 상태 머신을 만들어줘.

- 상태: Ready / Playing / GameOver / Cleared — enum + switch로 단순하게
- Ready에서 시작해 잠깐 뒤 Playing으로 (대기 시간은 인스펙터에서 조절)
- 플레이어 Health의 사망 이벤트를 구독해서 GameOver로
- WaveSpawner의 전체 클리어 이벤트를 구독해서 Cleared로
- GameOver / Cleared 에서: 커서 표시, Time.timeScale = 0
- 그 상태에서 R키를 누르면 현재 씬을 다시 로드
  (Time.timeScale을 1로 되돌리는 것을 잊지 말 것)
- 상태가 바뀌면 C# 이벤트로 알릴 것 — HUD가 구독할 것이다
- 구독한 이벤트는 OnDisable에서 반드시 구독 해제할 것
- GameOver / Cleared 로 갈 때 플레이어 조작을 멈출 것.
  timeScale = 0 은 Update를 멈추지 않아서, 안 끄면 죽은 뒤에도 총이 나간다
  PlayerController 와 WeaponSystem 을 각각 [SerializeField] 로 받아 enabled 를 끌 것.
  배열이나 리스트 하나로 묶지 마 — 타입이 넓어지면 인스펙터에서 엉뚱한 것도 들어간다
- Esc로 게임을 종료할 것 (Application.Quit). 어느 상태에서든 눌리게
- R키와 Esc는 InputSystem_Actions 에셋에 액션이 없다.
  WeaponSystem의 재장전처럼 코드에서 InputAction을 만들어 쓸 것

파일: Assets/Scripts/Core/GameManager.cs 하나만 생성.
WaveSpawner와 PlayerController는 수정하지 마.
씬은 건드리지 말고 세팅 절차만 알려줘.
```

**결과**:
- `GameManager.cs`가 만들어졌습니다. 상태는 준비, 플레이, 게임오버, 클리어입니다.
- 컴파일 에러가 없었습니다.

**문제점**:
- 코드를 만들 때는 눈에 띄는 문제가 없었습니다.
- 직접 플레이해 보니 로그와 추락 문제가 나중에 나왔습니다. (아래 시도 2, 3)

**원인 분석**:
- 만드는 단계에서는 컴파일만 확인했고 실제 플레이는 아직이었습니다.
- 문제는 직접 해 보면서 하나씩 나타났습니다.

## 3-3 — 게임필

### 시도 1
> 타격감 3가지를 하나씩 넣기 — 먼저 적 피격 시 흰색 깜빡임

```
타격감을 넣어줘. 단, 한 번에 하나씩 하고 매번 내가 테스트할게.

1) 적 피격 시 머티리얼을 0.05초 흰색으로 플래시
2) 피격 시 카메라 셰이크 (0.1초, 강도는 인스펙터에서 조절)
3) 명중 지점에 파티클

1번부터 시작해. 2번은 내가 말하기 전에는 하지 마.
```

**결과**:
- 적이 맞으면 흰색으로 깜빡이게 만들어졌습니다.
- 한 번에 하나씩, 매번 내가 테스트하는 방식으로 진행했습니다.

**문제점**:
- 이 단계에서는 눈에 띄는 문제가 없었습니다.
- 다음 단계(카메라 셰이크)에서 문제가 나왔습니다.

**원인 분석**:
- 해당 단계는 단순해서 문제가 없었습니다.
- 한 번에 하나씩 하기로 해서 문제가 생겨도 어디서 생겼는지 바로 알 수 있었습니다.

```
안흔들려
```

- 이후 "내가 맞을 때도 있으니 좋다"며 해석을 받아들이고 다음 단계로 갔습니다.

**결과**:
- 카메라 셰이크가 느껴지지 않았습니다.
- 문제가 두 가지가 겹쳐 있었습니다.

**문제점**:
- 카메라가 안 흔들렸습니다.
- 내가 기대한 상황(적을 쏠 때)에서는 아무 반응이 없었습니다.

**원인 분석**:
- "피격 시"가 누가 맞는 건지 안 적어서 플레이어가 맞을 때로 만들어졌는데, 나는 적을 쏘면서 테스트했습니다.

**배운 점**:
- "누가 맞을 때"처럼 대상을 적어야 합니다.
- 실패했을 때는 바로 고치기보다 왜 안 됐는지부터 보면 해석 차이가 드러납니다.

## 3-4 — AI 코드 리뷰

### 시도 1
> 스크립트 전체를 5가지 관점으로 리뷰 (고치지는 않고)

```
지금까지 작성된 Assets/Scripts 전체를 리뷰해줘.

다음 관점으로 문제를 찾아 심각도 순으로 정리:
- Update()에서의 불필요한 연산 / GetComponent 호출
- null 참조 가능 지점
- 이벤트 구독 해제 누락 (메모리 누수)

각 항목마다 파일:줄 번호와 수정 방향을 제시하되, 아직 고치지는 마.
```

**결과**:
- 문제점 여러 개를 심각도 순으로 받았습니다.
- 각 항목에 파일과 줄 번호, 수정 방향이 같이 있었습니다.

**문제점**:
- 지적이 전부 맞는지는 내가 직접 확인해야 했습니다.
- 항목이 많아서 어떤 걸 먼저 고칠지 정해야 했습니다.

**원인 분석**:
- AI의 리뷰도 틀릴 수 있습니다. 코드를 읽는 것과 실제로 일어나는 일은 다를 수 있습니다.
- 그래서 고치기 전에 한 번씩 맞는지 따져 보기로 했습니다.

### 시도 2
> "캐시가 무제한으로 늘어난다"는 지적이 틀린 것 같다고 질문

```
<9. 캐시가 무제한으로 늘어난다>는 틀린 것 같아. 키는 총알에 맞은 콜라이더라서 씬에 있는 콜라이더 수로 제한되고 있는거 아니야?
내가 잘못 이해한 건지, 지적이 틀린 건지 확인해줘.
```

**무엇을 바꿨나**:
- 지적을 그대로 따르지 않고 틀린 것 같다고 되물었습니다.
- "내가 잘못 이해한 건지, 지적이 틀린 건지"를 같이 물어서 내 생각도 틀릴 수 있다는 여지를 남겼습니다.

**결과**:
- 캐시 키가 총알에 맞은 콜라이더라서 씬의 콜라이더 수(약 105개)로 한정됩니다. 내 말이 맞았고 AI의 지적이 틀렸습니다.
- 이 지적은 고치지 않기로 했습니다.

**배운 점**:
- AI 지적도 확인해 보고 고치자. 그대로 따르면 쓸데없는 코드를 넣게 됩니다.
- 맞는지 아닌지를 근거와 같이 물으면 답이 분명해집니다.
